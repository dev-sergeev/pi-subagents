# Спецификация: совместимость инструментов с GigaChat

Статус: реализовано и проверено на Pi `0.85.1`, закреплённом неизменённым `pi-gigachat@0.6.4`, согласно уточнению заказчика. Все 35 итоговых provider-path объявлений из 13 сценариев приняты официальным валидатором по правилам `1.0.6`. Единый финальный прогон всех шести live-сценариев `GigaChat-3-Ultra` прошёл; схемы, ответы, аргументы, исполнение, возврат результата модели и локальные проверки сохранены в [доказательствах приёмки](../examples/gigachat-compatibility/README.md).
Основание: проверка `pi-subagents@0.79.1` от 19.10.2026 — 33 запроса [официальному валидатору](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/function-validation.md), правила `1.0.6`.

## Цель и границы

Все объявления инструментов пакета должны проходить валидацию GigaChat и сохранять существующие сценарии делегирования. Совместимость — контракт форка по умолчанию, без отдельного режима, нового провайдера или универсального преобразователя JSON Schema. Полномочия, supervision и семантика запуска/завершения сохраняются; для целевого Pi используются его поддерживаемые механизмы system prompt/tools и очереди follow-up. Это соответствует [VISION.md](../VISION.md).

## Обязательные изменения

### 1. Явные типы `workflow` и `output`

В модельной схеме `subagent` заменить смешанные `anyOf` на `type: "string"` с точным описанием значений:

- `workflow`: `"true"` — блок `js workflow` из текущего ответа; путь — скрипт из файла; другое допустимое имя — workflow-ресурс. Отсутствующее поле сохраняет запуск одного агента или management-действия.
- `output`: путь — сохранение результата; `"false"` — отключение сохранения; `"true"` — применение настроенного вывода по умолчанию. Отсутствующее поле сохраняет прежние правила наследования.

Эти строковые формы уже поддерживаются в [нормализации workflow](../src/extension/public-execution.ts), [чтении блока ответа](../src/extension/reply-workflow-script.ts) и нормализаторах вывода: [child-launch-plan](../src/runs/shared/child-launch-plan.ts), [single-output](../src/runs/shared/single-output.ts). Проверить согласованность всех путей; не просто дописать `type`, оставив булевы значения в подсказках. Булевы формы убрать из публичного модельного контракта и его примеров; внутреннее представление выполнения можно сохранить.

### 2. Полные описания параметров

У каждого непосредственного свойства `parameters.properties` должны быть явный строковый `type` и непустой, содержательный `description`. Исправить подтверждённые пропуски:

| Инструмент | Параметры без описания |
| --- | --- |
| `contact_supervisor` | `reason`, `message`, `interview` |
| `subagent_supervisor` | `action`, `to`, `replyTo`, `replyText` |
| `subagent_command` | `action`, `toolCallId`, `waitMs` |
| `watchdog_warn` | `category` |
| `watchdog_ask` | `question`, `evidence` |
| `watchdog_permission_decision` | `decision` |

Herdr-вариант `contact_supervisor` привести к согласованному объявлению: `reason` — строковый enum, `interview` — явно описанный объект по протоколу интервью, не `Type.Unknown`. Не кодировать объекты строками ради прохождения валидатора.

Согласованное после live-проверки изменение: у родительского `subagent_supervisor` поле ответа называется `replyText`, без алиаса `message`; запросы `pending`/`status`/`list` не требуют текста. `contact_supervisor.message` и внутренние записи транспорта не меняются. На минимальных реальных запросах Ultra пропускала optional `message`, но передавала optional `replyText`; переименование явно одобрено заказчиком.

Порядок свойств родительского объявления сохраняется как `action`, `to`, `replyTo`, `replyText`: адресат предшествует тексту. Обратный порядок в полном live-сценарии приводил к пропуску optional текста; целевой порядок прошёл реальный диалог без уточнения. Проверять фактическую сериализацию и выполнение, а не только семантическое равенство JSON Schema.

### 3. Структурированный результат

В `structured_output` сохранить пользовательскую схему `value` и её ограничения. Если у её корня нет `description`, добавить правдивое описание назначения результата, не изменяя пользовательский объект схемы. Описать `acceptanceReport`, сохранив существующую проверку его содержимого и обязательность при соответствующей конфигурации. Проверять итоговую обёртку: валидность исходного `outputSchema` сама по себе недостаточна.

### 4. Единый действующий контракт

Изменения охватывают обычные и structured workflow, fanout, дочерние инструменты, watchdog и Herdr. Обновить обработчики, затронутых вызывающих, prompt/guide-тексты, примеры, тесты и changelog. В этом форке новый механизм `declaration-pinning` удалён: регистрируются только текущие схемы, а неподдерживаемая история `system`/tool declarations/sections требует новой сессии. Не добавлять legacy-алиасы или второй режим поведения.

## Что не является обязательным исправлением

- Вложенные свойства без `description`, свободные объекты и пустой `properties` проходили проверенные случаи `1.0.6`. Не вводить неподтверждённые запреты на все `anyOf`, `$ref` или `const` и не удалять ограничения схем ради валидации.
- Отсутствие `return_parameters` и `few_shot_examples` допустимо как два известных предупреждения. Их передача через `pi-gigachat` — отдельная задача, не условие этой доработки.
- Полная переработка `options`, смена npm-имени, миграция провайдера `pi-gigachat` и одновременная поддержка разных поколений Pi вне объёма работ. Целевая версия этого форка — `0.85.1`, а не адаптация провайдера к новому Pi.

## Критерии приёмки

1. Собрать реальные итоговые объявления всех инструментов после обычного пути Pi → GigaChat, включая активацию `subagents_enable`, `bg_wait`, `watchdog_diff`, обёрнутый `bash` и все перечисленные условные варианты. Каждый запрос `/functions/validate` возвращает `message: "Function is valid"` без `errors`. HTTP 200 сам по себе не считается успехом. Сохранить схемы, полные ответы и `json_ai_rules_version` без ключей и токенов; предупреждения допустимы только о двух указанных необязательных полях.
2. Поведенческими тестами подтвердить выбор reply/file/resource workflow, сохранение/отключение/наследование вывода, отклонение некорректных модельных аргументов и сохранение проверок structured output/acceptance report. Для structured output проверить схемы с корневым описанием и без него, с отчётом и без него.
3. На совместимых между собой Pi и GigaChat-провайдере выполнить живые smoke-сценарии: одиночный агент, workflow, async-результат и ожидание, supervisor-диалог, structured output, watchdog. Проверить не только загрузку объявления, но и аргументы, выполнение и возврат результата модели.
4. Обновлённые подсказки используют только новый контракт; перезапуск/новая сессия не восстанавливают несовместимые объявления. Существующие unit/integration-проверки и сборка проходят, устаревшие проверки заменены проверками действующего поведения.
